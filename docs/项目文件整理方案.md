## 五、风险与必须先修的坑

### 5.1 ⚠️ 严重：`uploads` 路径不一致（**2026-09-01 复核后已修正结论**）

**关键前提（初次盘点时漏看，导致结论反向）**：
- `docker-compose.yml:99` → `- ./uploads:/app/uploads`，把**根 `uploads/`** 挂进容器；
- `backend/Dockerfile` → `WORKDIR /app` + `COPY . .`，故容器内代码位于 `/app/app/...`；
- **当前生产是容器运行**（`ssm-backend` Up 11 hours）。

**逐路径实算**（`Path(__file__).parent` 第 1 级 = 文件所在目录）：

| 代码位置 | 容器内解析 | 宿主机裸跑解析 |
|---|---|---|
| `public.py:1169,1204,1249`（4 级 parent） | `/app/uploads` ✅ | `backend/uploads` ❌ |
| `bid_attachments.py:19`（dirname + `..`×3） | `/app/uploads` ✅ | `backend/uploads` ❌ |
| `intent_crawler.py:437`（3 级 parent） | `/app/uploads` ✅ | `backend/uploads` ❌ |
| `intelligence_admin.py:1057`（**5 级** parent） | `/uploads` ❌ **BUG** | 根 `uploads/` ✅ |

**真实后果**（与初版判断不同）：
1. 容器内 3 处都正确指向 `/app/uploads` = 宿主机**根 `uploads/`**；**130 条附件记录可正常下载**（占绝大多数）。
2. `intelligence_admin.py` 是**唯一 BUG**：容器内写到 `/uploads`（容器可写层，重启即丢），宿主机裸跑才写到根 `uploads/`。
3. 另有 **10 条附件**（宿主机裸跑爬虫产生，id 216/217/218/219/220/239）落在 `backend/uploads`，而**该目录未挂进容器 → 容器环境下这 10 条 404**。
4. `intent_attachment.local_path` 存的是**相对 uploads 的相对路径**（如 `intent_attachments/97/xxx.docx`），共 140 条，其中 **10 条 `local_path` 为空**；`bid_attachment` 5 条前缀为 `bid`。

> 结论：**统一目标目录应为根 `uploads/`**（与 compose 挂载一致、且 130/140 的数据在此），**不是** `backend/uploads/`。初版推荐方向错误，特此更正。

**处置方案（已获批准执行）**：
1. 新增 `backend/app/utils/upload_paths.py`，用显式判定替代层级魔法：
   ```python
   def upload_root() -> Path:
       env = os.getenv("UPLOAD_DIR", "").strip()
       if env: return Path(env)                      # 最优先: 显式环境变量
       if Path("/app/uploads").is_dir(): return Path("/app/uploads")   # 容器内挂载点
       return Path(__file__).resolve().parents[3] / "uploads"          # 裸跑: 仓库根
   ```
   （裸跑时 `upload_paths.py` 位于 `backend/app/utils/`，`parents[3]` 即仓库根）
2. 上表 4 处调用全部改为 `upload_root()`；
3. `docker-compose.yml` backend 环境补 `UPLOAD_DIR: /app/uploads`（显式锁定）；
4. 把 `backend/uploads/**`（intent_attachments 216~220、239；bid 344~348）**合并移动**到根 `uploads/`（id 目录不冲突：根为 97~213），随后删除 `backend/uploads/`；
5. `local_path` 是相对路径，合并后**无需改库**。
